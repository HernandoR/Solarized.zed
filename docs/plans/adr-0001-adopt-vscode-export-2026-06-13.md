# ADR-0001: Adopt VSCode Export as Source of Truth for Zed Theme Colors

- Status: Accepted (surface shades superseded by
  [ADR-0003](adr-0003-computed-surface-ladder-2026-06-26.md))
- Date: 2026-06-13

> Note: the syntax/hue mapping below still stands. The seven intermediate
> **background** shades this ADR introduced were later replaced by a computed
> CIELAB lightness ladder — see ADR-0003.

## Context

This repository hosts the "Solarized" theme extension for the Zed editor (originally authored by harmtemolder). The theme is currently generated by `solarized.py`, which maps the canonical Solarized 16-color palette (base03, base02, …, yellow, orange, red, magenta, violet, blue, cyan, green) into Zed's theme style keys.

Separately, the user maintains a VSCode Solarized theme (`solarized.jsonc`) that includes personal UI tweaks accumulated over time — darker panel/sidebar backgrounds, fine-tuned selection highlights, custom input field colors, and adjusted focus indicators. This VSCode export represents the user's actual day-to-day editing environment.

The two have drifted: the Zed theme uses a clean/vanilla palette mapping, while the VSCode theme has the user's real-world customizations. The name "Solarized" implies a shared visual identity, but the different environments render differently because of these accumulated tweaks.

## Decision

> In the context of maintaining visual consistency across editors,
> facing the divergence between the canonical Zed theme and the user's actual VSCode setup,
> we decided for adopting the VSCode export (`solarized.jsonc`) as the reference for Zed theme values,
> and against keeping the two independent,
> to achieve pixel-level consistency between the user's VSCode and Zed environments,
> accepting that some VSCode-specific color keys have no direct Zed equivalent and will be dropped, and that the theme may become slightly less "vanilla Solarized" and more tailored to the user's preferences.

Concretely:

1. **Update `solarized.py`** to add a `base03_dark` color (`#00212b`) for surfaces the user customized to a shade darker than base03, plus any intermediate colors (e.g. `#004052`, `#003847`, `#005a6f`) used in the VSCode export.

2. **Preserve the programmatic approach** — `solarized.py` stays as the single source of truth; the VSCode colors inform the palette expansions, not a separate hardcoded copy.

3. **Active-only adoption** — Only the ~50 uncommented color keys in `solarized.jsonc` will be mapped. The ~500 commented-out keys (VSCode defaults the user never touched) are ignored.

4. **Token colors** — The `tokenColors` array in `solarized.jsonc` already matches the canonical Solarized syntax highlighting. The existing `syntax` block in the Zed theme maps correctly and needs only minor alignment.

5. **Light mode** — The light variant in `themes/solarized.json` uses the canonical inverted palette. The VSCode export only has a dark variant, so the light variant continues to use the standard inversion approach.

## Consequences

### Positive
- The Zed theme will match the user's actual VSCode appearance pixel-for-pixel for dark mode.
- Future VSCode tweaks can be ported systematically by diffing `solarized.jsonc` changes.
- The programmatic generator is preserved — no hardcoded JSON editing needed.

### Negative
- Some VSCode keys (e.g. `activityBar.background`, `editorGroupHeader.tabsBackground`) map awkwardly to Zed's coarser semantic model; exact fidelity isn't always possible.
- The theme loses some of its "vanilla" character — surfaces that were uniform base03 or base02 now use intermediate shades.

### Risks
- The VSCode export may be subject to future change; diffing discipline is needed to stay in sync.
- `solarized.jsonc` contains some colors that are VSCode-internal implementation details (e.g. `editorWhitespace.foreground` with transparency); these may not translate to Zed's model.
